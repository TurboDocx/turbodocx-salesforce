# TurboSign for Salesforce 1.1.0 — QA findings (2026-10-12)

**How tested:** package **1.1** (`04tbm000000o8LlAAI`) was installed from the docs' production link into a fresh Developer Edition. The admin setup followed TurboDocx/Docs#206 page by page, then send, preview, sign and write-back were run end to end against the upcoming TurboDocx backend and frontend.

**Result:** install, setup, send, sign, write-back (signed PDF, audit trail, Closed Won), the Signatures panel (refresh after send, Remind, Void) and reconnect all work. Four package bugs and one accessibility point are below. None blocks the release.

**Status: all five are fixed in this PR**, test first:
- LWC Jest: 99 passing.
- The Apex fixes ran in the QA Developer Edition org: all 154 package Apex tests pass.
- Each fix was then re-checked by hand in that org (details under each item).

## Bugs

### P1. "Required value" toast drops the token name — medium
- **Repro:** an Opportunity with no Account and a setup whose `{ClientName}` (Account Name, Required) is empty → Send for Signature → Review → Send.
- **Expected** (what the docs promise): *"Required value `{ClientName}` is empty on this record. …"*
- **Actual:** the toast says *"Send failed: Required value is empty on this record. Fill in its source field or mark it optional in TurboSign Setup."* The send is blocked correctly, but the rep can't tell which field to fill.
- **Cause:** `TurboSign_Log__c` stores the full text with `{ClientName}`. `ShowToastEvent` treats `{…}` in `message` as a format placeholder and removes it.
- **Fix idea:** in `turboSignSendModal.js`, show Apex messages through `message: '{0}', messageData: [text]` on all three error toasts (refused, "Check before sending again", and the thrown-error `catch`). Other toasts that echo Apex text (e.g. the builder's) need the same.
- **Fixed:** a shared `c/turboSignToast` helper passes every toast's text as `messageData`. The send modal, the Signatures panel and the builder all use it.
  - **Re-test:** sending from an Opportunity with no Account now shows *"Required value {ClientName} is empty on this record. …"*.

### P6. "Check before sending again" is lost when the database refuses writes — medium
- **Repro (found by accident):** the org's file storage was over its limit (a 21 MB test file in a 20 MB Developer Edition). Send for Signature → Review → Send.
- **Actual:** TurboDocx **sent** the document (signer emailed, backend 200), but the rep saw *"Send failed: The document could not be sent. Try again."* No envelope row, no log row. A retry sends a duplicate.
- **Debug log:** both callouts 200 → `insert TurboSign_Envelope__c` (TurboSignService:156) `STORAGE_LIMIT_EXCEEDED` → the `catch` in `TurboSignQuickActionController.sendForSignature` runs `insert as user new TurboSign_Log__c(...)` (line ~93), which fails the same way → the exception escapes, so the `{ ok:false, maybeSent:true }` result never returns and the LWC falls back to the generic toast.
- **Fix idea:** make the log insert unable to throw (`Database.insert(log, false)` or a try/catch), so `maybeSent` always reaches the rep. Any DML failure at stage `record` (validation rule, trigger, storage) hits the same path.
- **Fixed:** the log insert is best effort (try/catch).
  - **Apex test:** a user who can't create log rows still gets the answer.
  - **Re-test:** with file storage over its limit again, the rep sees **Check before sending again**, *"TurboDocx may already have sent this document. Check before sending again. (… STORAGE_LIMIT_EXCEEDED …)"*.

### P4. Builder "Preview values" shows raw dates — low
- **Repro:** TurboSign Setup → `{EffectiveDate}` from Close Date, Date Format blank → Test with a record → Preview values.
- **Actual:** `2026-08-05 00:00:00`. The real send shows `11/15/2026` (the user's locale), and the docs say dates follow the sending user's locale.
- **Cause:** `TurboSignConfigController.previewPayload` returns `String.valueOf(val)` with no formatting, while the send path (`TurboSignRequestBuilder`) sets `formatPaths` (native FORMAT) or applies `Date_Format__c`.
- **Fix idea:** reuse the send's formatting (`nativeFormatPaths` / `applyDatePattern`) in `previewPayload`, so the preview equals what is sent.
- **Fixed:** `previewPayload` now goes through the send's own `TurboSignRequestBuilder.resolveValues` and `resolvedText`.
  - **Re-test:** Close Date now previews as `10/12/2026` with no Date Format, and `October 12, 2026` with `MMMM d, yyyy`.

### P5. Grammar in the builder — cosmetic
- `turboSignConfigBuilder.html:296` reads *"Pick a {sourceObject} record …"*, which renders as "Pick a Opportunity record". Suggest *"Pick a record to see …"*, or the article from the object label.
- **Fixed:** the hint now reads *"Pick a record to see the values these mappings resolve to."*

## Accessibility

### A1. Many buttons share the name "Remove"
The document-name chip ×, the recipient row and the token row delete buttons all have `alternative-text="Remove"`. Screen readers (and test automation) can't tell them apart. During QA this led to removing the wrong item (a document-name field instead of a recipient). Suggest labels such as *"Remove Account.Name from the document name"*, *"Remove signer 2"*, *"Remove token {date}"*.
- **Fixed:** each remove button names what it removes:
  - a text piece by its words, for example *Remove "Service Agreement - " from the document name*;
  - a field by its path;
  - *the date*;
  - *signer N*;
  - *token {x}*.
  - **Re-test:** on Service Agreement, the 9 remove buttons have 9 distinct names.

## Not a package bug (for the record)
- **Send for Signature in the ▼ menu:** added through the page layout, the action lands at the end of the list, and the Highlights Panel shows 3 buttons. This is a docs fix (Docs#206).
- **Preview shows blank signing spots:** intended. The sample template renders `{sig}` / `{date}` in white (`unpackaged/sample/__tests__/serviceAgreement.test.js`). The docs sentence saying they "still show as their tokens" is what needs fixing.
- **Dev note:** `serviceAgreement.test.js` shells out to `unzip`, so on a machine without it `npm test` fails that one suite with "Converting circular structure to JSON". CI has `unzip`.
